# 第一性原则 Skill

当面对编程问题时，使用第一性原理思维（First Principles Thinking）——将问题分解到最基本的不可再分的真理，然后从这些基础真理向上推导解决方案。**不要依赖类比、行业惯例或"大家都这么做"。**

---

## 核心原则

### 1. 分解到不可再分的基本单元

对任何复杂系统，持续追问"为什么"直到触及物理/数学/逻辑层面的基本真理：

```
用户问题
  → 这本质上是一个什么问题？（数据处理？状态协调？资源竞争？）
    → 这个操作在计算机层面是什么意思？（CPU指令？内存读写？网络IO？）
      → 操作系统/语言运行时在这里提供的原语是什么？
```

**例：** "这个 React 组件重渲染太慢"
- 第一性原理追问：React 的重渲染机制本质是什么？（虚拟 DOM diff → 真实 DOM patch）
- 什么决定 diff 成本？（组件树规模、props 变化频率、渲染函数计算量）
- 有哪些基本策略？（跳过不必要 diff、减小 diff 范围、减少 diff 触发频率）
- → 具体选择：`React.memo`（跳过）、`useMemo`（减小范围）、状态提升下移（减少触发）

### 2. 拒绝类比推理

常见陷阱：

| 类比推理 | 第一性原理 |
|---|---|
| "大家都用微服务，所以我们也用" | "我们的系统瓶颈在何处？单体架构是否能满足未来 6 个月的需求？" |
| "这个模式是最佳实践" | "这个模式解决了什么具体问题？我们真的有这个问题吗？它的代价是什么？" |
| "上一家公司就是这么做的" | "当时的约束条件是什么？现在相同吗？过去的方案在当前上下文是否最优？" |
| "这个库很流行" | "这个库解决了什么基本问题？我们用原生 API 需要多少代码？引入依赖的增量成本是否值得？" |

### 3. 物理极限思维

在考虑工程决策时，先问物理极限在哪里，再反推合理方案：

```
物理极限
  → 理论最佳值（不可能超越）
    → 工程最佳值（无限资源下可达）
      → 当前工程方案（在给定约束下折中）
```

**例：** 排序 100 万条记录
- 物理极限：`O(n log n)` 比较次数，`n` 条数据必须至少读一次
- 理论最佳：快速排序/归并排序 ≈ 20M 次比较
- 工程最佳：并行排序 + SIMD ≈ 50ms
- 当前方案：JavaScript `Array.sort()` 大约 200ms → 对大多数场景已经够用

### 4. 约束条件的显式化

每个工程决策都是在一组约束条件下的优化。**显式列出约束：**

```
约束类型：
- 时间约束：需要在什么时间内完成？（运行时/开发时间/响应时间）
- 资源约束：CPU/内存/网络带宽/存储的可用量？
- 维护约束：将来谁维护？他们对这个方案的熟悉程度？
- 兼容约束：需要支持哪些环境/版本/接口？
- 正确性约束：一致性要求有多严格？（ACID vs 最终一致）
```

## 问题分解框架

### 性能问题

```
1. 测量 → 瓶颈在哪里？（不要猜测）
   - 用工具直接测量：`api_request` / `read_process_log` / 数据库查询
2. 分解：
   - 等待型瓶颈（IO/网络/锁）：并行化、异步化、缓存
   - 计算型瓶颈（CPU）：算法优化、缓存计算结果、减少计算量
3. 验证：
   - 改前改后对比测量
   - 是否接近物理极限？若否，有机会继续优化
```

### 架构决策

```
1. 功能：这个系统必须做什么？（列出所有必须功能，不包含锦上添花）
2. 约束：哪些约束是不可妥协的？
3. 权衡：在满足 1+2 的前提下，哪个方案最简单？
4. 验证：能否在一个 Sprint 内用最小可行方案验证假设？
```

### 调试

```
1. 预期行为是什么？（从需求和代码逻辑出发）
2. 实际行为是什么？（用数据而非观察确认）
3. 从"代码的实际执行路径"反推，而非从"我认为代码做了什么"出发
4. 用工具验证每个假设：
   - `api_request` 测试 API 端点
   - `read_process_log` 查看日志
   - `edit_file` + 打印关键变量
   - `db_query` 检查数据状态
5. 定位到根本原因后，问：这个根本原因涉及的基本原理是什么？
```

## 编程中的第一性原理清单

| 原理 | 应用 |
|---|---|
| **幂等性** | 重复执行同一操作应产生相同结果 → REST API / 消息处理 / 重试逻辑 |
| **单一事实源** | 数据只在一个地方定义，其他地方引用 → 状态管理 / 配置 / 规范 |
| **无副作用** | 给定相同输入，函数始终返回相同输出 → 纯函数、缓存友好 |
| **局部性原理** | 最近访问过的数据很可能很快再被访问 → 缓存策略、数据布局 |
| **最简依赖** | 一个模块应当依赖尽可能少的其他模块 → 解耦、测试 |
| **失败原子性** | 操作要么完全成功要么完全不执行 → 事务、错误处理 |

## 反模式：什么时候 NOT 使用第一性原理

- **原型/探索阶段**：快速验证 > 从零推导。先抄后改。
- **非关键路径**：日报生成的排序算法用冒泡就可以，不需要推导最优解。
- **第三方依赖评估**：是否用 lodash 不必从 JS 原语推导，直接看 bundle size impact。
- **时间极度紧迫**：「先解决问题，再理解为什么能解决」比完整推理更合理。
